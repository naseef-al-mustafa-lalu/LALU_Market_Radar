# Lalu Atlas

Daily pipeline: NHS public data + Oscar contacts -> Supabase -> Slack posts (#lalu_market_radar) + login-protected dashboard (`index.html`).

## One-off setup
1. **Supabase** (project `qvdnpvouqecfsinsvvwf`, London): schema, triggers and RLS are already applied (`supabase/migrations`).
   - Dashboard -> Authentication -> Providers -> Email: **disable "Allow new users to sign up"**.
   - Authentication -> Users -> **Add user** (email + password) for each person. Then add their email (lower-case) to `allowed_users` via SQL editor: `insert into allowed_users values ('name@lalu.co.uk');`. Access needs both an account and an allowlist row.
2. **GitHub secrets** (Settings -> Secrets and variables -> Actions): `SUPABASE_URL` (https://qvdnpvouqecfsinsvvwf.supabase.co), `SUPABASE_SERVICE_ROLE_KEY` (Supabase -> Settings -> API; never put this in the repo or index.html), `OSCAR_API_URL`, `SLACK_WEBHOOK_URL` (see step 3).
   (`OSCAR_API_URL` is optional: without it practices load with no contact data; add it later and the next run fills contacts in.) **Variables**: `DASHBOARD_URL`, optional `SLACK_MODE` (ON|DISABLED), `MIN_TIER_ALERT` (Tier 1|2|3).
3. **Slack** (new signals are posted to `#lalu_market_radar`): at api.slack.com/apps create an app (from scratch) > *Incoming Webhooks* > turn on > *Add New Webhook to Workspace* > choose `#lalu_market_radar` > copy the URL into the GitHub secret `SLACK_WEBHOOK_URL`. (Alternative: a bot token with `chat:write` in the secret `SLACK_BOT_TOKEN`, invited to the channel, and the variable `SLACK_CHANNEL`.) Until a secret is set the run still succeeds, shows a warning, and leaves signals unsent so they post once Slack is set up. Variables: `SLACK_MODE` (`ON` or `DISABLED`), `MIN_TIER_ALERT` (default `Tier 3`), `DASHBOARD_URL` (used for the links).
4. **GitHub Pages**: Settings -> Pages -> deploy from `main` / root. (Private repos need a paid GitHub plan for Pages.)
5. Run the **Daily market radar** workflow manually once. The first successful run is a silent *baseline*: it loads everything but raises no triggers and sends no email. From the second run, changes generate signals.

## Signals workflow and shareable views
Each signal has a status (New, In progress, Done, Dismissed) and a note, set in the Signals feed (the feed shows open signals by default). The web address carries the tab, filters, sort, selected network and open practice, so any view can be bookmarked or shared. Rows, headers and the side panel work from the keyboard (Tab, Enter / Space, Esc).

## Northern Ireland and the Isle of Man
Both come from ODS each day (`other_uk_step` in `src/ingest.py`, database function `ingest_other_uk`): Northern Ireland's practices are ODS role RO315 (Z codes, about 305), the Isle of Man's are the 12 listed in `IOM_CODES` in `src/sources.py` (Y codes; the island's non-GP Y records, such as the hospice, are not practices). New ones are added with country set, no PCN or list size and no NEW_PRACTICE signals; existing rows are left alone, and nothing is closed automatically. HubSpot companies carrying these codes stop showing as "Not a GP practice code" in the audit once the practice exists.
List sizes are uploaded in Data > Data sources. **Isle of Man** box: the health service's annual registrations return (`practice-registrations-….csv`; a sample is in `tests/fixtures/`). Practice names in the file map to ODS codes (`IOM_PRACTICES` in `js/data-uploads.js`), the last column (total after age re-assessment) is the list size, and the quarter date becomes the data month. The first load used the March 2020 return (data month 2020-04), so those sizes are a 2020 snapshot until a newer return is uploaded. Promenade (in the 2020 return) is no longer an active ODS practice and is skipped. **Northern Ireland** box: the Department of Health / BSO "General Medical Services Statistics for NI" quarterly workbook (`fps_gms_quarterly_tables_….xlsx`; the Q1 2026/27 workbook is in `tests/fixtures/`). Atlas reads **sheet 7.1** (registered patients by practice) straight from the .xlsx (a zip of XML, inflated with the browser's `DecompressionStream`, no spreadsheet library) or from that sheet saved as CSV. The ODS code is `Z` + the practice number padded to five digits (every one of the 305 NI practices matched), the last column is the latest quarter's list size, and `[c]` marks closed practices, which are skipped. The financial quarter becomes the data month (Q1 = June, Q2 = September, Q3 = December, Q4 = March). The 304 reporting practices total the published 2,080,799. Quarterly figures are provisional until the annual publication.

## Data sources (what feeds the central database)
The dashboard's **Data > Data sources** tab opens with a **Connections** card for every integration (what it is for, when it runs, which secrets and scopes it needs, what breaks if it fails, and a health chip from the latest run). It has a **Test connection** button that runs read-only checks of the HubSpot token (companies, contacts, deals, leads, pipelines, owners, line items). Keep it true by editing `CONNECTIONS` in `js/data-tab.js` whenever an integration is added or changed. The HubSpot token lives in two places, the GitHub secret (sync) and the Supabase function secret (actions): rotate both together.

| Source | Gives | Cadence |
|---|---|---|
| NHS ODS API + ODS export | Active GP practices, names, postcodes, closures, PCN and ICB | Daily, automatic |
| NHS Digital patient register | Patient counts (tiers, growth) | Monthly, upload in the dashboard (or runner) |
| Oscar Research file | Contacts (name, title, dept, email/phone, opt-outs) and practice details (address, federation, GP numbers, employees, spend, notes, Oscar IDs) | Daily, when `OSCAR_API_URL` is set |
| CQC public API | Registration status, overall rating, last inspection, registered-manager absence | Daily via the changes feed (first run backfills over one or more days) |
| CQC providers | Group name and size (e.g. Modality) for providers running 2+ practices | Daily |
| Practice websites | Cautious clinical-system hint | Daily, capped |

Signals: new practice, practice closed (merger), rapid growth, PCN move, new manager, plus CQC: registration ended, rating changed,
new inspection, registered manager absent, practice changed operator (likely takeover). CQC signals only fire after a first CQC value is stored, so the initial load is silent.
Requires the `CQC_API_KEY` secret (free key from the CQC API portal).

## Pricing, tiers and estimated ARR
Tiers and ARR follow Lalu's pricing model (the "Patient Size Threshold Analysis For Discounts" sheet) and are driven by two editable tables
in Supabase, so nothing is hard-coded:
- `pricing_tiers`: per route (`practice`, `pcn`, `icb`; `group` / `federation` allowed when you define them) the patient threshold, size discount and optional speed discount for tiers 1-5.
- `pricing_settings`: list prices per patient per month (All reports and SAR only, annual and monthly), term discounts, price floor (All reports), VAT.
Rates are per patient per **month**; Est. ARR = patients x price x 12. Two products: **All reports** (annual 0.08 / monthly 0.10) and **SAR only** (annual 0.05 / monthly 0.06). Discounts apply to **annual plans only** (monthly has none): price = list x (1 - size - term - speed), with the price floor protecting All reports only. The optional speed discount (off by default) applies to every year of the term and ends at renewal. The practice and network tables carry a "SAR ARR" column; the Revenue tab has an All reports / SAR only / Mix scenario with an editable SAR-only share.
The views `practice_pricing` and `org_pricing` calculate it live, so editing a row (Supabase -> Table Editor) updates the dashboard immediately.
The dashboard shows it per practice, per network (Networks tab) and in the **Revenue** tab (route totals, tier breakdown, pipeline by lead status, rate card).
Provider groups and federations are priced on the aggregate patients of their linked practices (seeded from the PCN schedule; edit the `group` / `federation` rows in `pricing_tiers`). The routes are alternative ways to sell to the same patients: do not add them together. `MIN_TIER_ALERT` (Tier 1-5) uses the single-practice tiers.

## HubSpot status (what the dashboard reads)
The company's **Commercial Model** (HubSpot property `current_subscription`, which HubSpot clears at churn) is stored as `gp_practices.hubspot_commercial_model` and makes the practice a customer even with no deal or a lead lifecycle stage. **Freemium** customers show as their own status ("Freemium", filter "Freemium customers", own card in the revenue pipeline), have no deal prompt in the profile, and are left out of the customer ARR on the Networks tab (migration `20261021000033`): they bring no revenue.

**Contracted ARR** (migration `20261021000034`): the daily sync stores HubSpot's real money per practice. `hubspot_contracted_arr` is the summed ACV (`actual_annual_contract_value__acv_`) of the company's Services in a live stage (In Contract, Renewal Period, Renewed, Within 4 weeks of Cancellation Notice; pilots, freemium and churned/ceased are excluded; see `LIVE_SERVICE_STAGES`). With no live Service it falls back to closed-won Sales/Conversion deal amounts for a non-Freemium customer and is flagged `hubspot_contracted_src = deal` (shown with * as unverified). `hubspot_pipeline` is the open Sales (new-business) deal amount and `hubspot_conversion_pipeline` the open Conversion deal amount, which moves Freemium customers to ReportSure now that Freemium is discontinued (raw, not weighted; migration `20261021000037`) and `hubspot_renewal_pipeline` the open Renewals amount. The Revenue tab shows TAM, contracted ARR, open pipeline, renewals and headroom for the single-practice route (contracted ARR is route-independent); the practices table has a Contracted ARR column with the difference from the estimate. Needs the HubSpot token to read Services; if it cannot, the sync records `service_error` and uses deals only.

Dates: the profile's Contract section (paying customers with a contracted value) shows start and renewal date from the live Service (`hubspot_contract_start`/`hubspot_contract_end`, migration `20261021000036`); it replaces the Pricing section for them.

**Price card terms** (`js/practices.js`, `priceCard`): the 1, 2 and 3 year term tiles show **MRR** first (the contract states monthly recurring revenue) with **ARR** underneath; the *Price by year* table has Period, Discount, Per patient, **MRR** and **ARR** columns for each year, the multi-year total (in ARR) and the renewal year. The *Other ways to sign this practice* cards (`routeComparisonBody`) follow the same rule: MRR first, ARR beneath, the per-patient rate, and the difference against signing alone in both MRR and ARR.

**Referral group** (`js/referral.js`, pushed to HubSpot from the Push pricing screen): a referring practice who can sign other practices is priced on the combined list size. On a practice's price card, the "Referral group" row opens a panel: a ladder of the single-practice size-discount steps with an Alone and a Group marker, the practices in the referring practice's PCN to tick (customers show a badge and cannot be added), a search for any other practice or manual patients, and a result card (alone against group price, the saving, the conditional pill and a copy-able summary). The speed discount, term and product always come from the price card, never from the panel. The extra discount is the group's size discount minus the practice's own (`referralFor`), shown as its own "Referral group discount" line in the breakdown and conditional on the others signing within `REFERRAL_DAYS` (90). HubSpot: a deal property `referral_discount` ("Referral Discount %") exists; `HS_REFERRAL_WRITES` in `js/referral.js` is `false`, so the Push bar still sends the practice's own price (and says the group is not pushed) until HubSpot's Total Discount % calculation includes `referral_discount`. Still to build once it does: write `referral_discount` and the line item, the note on each deal, the deal-to-deal link and the "Reprice to alone" revert.

**Matching rules for signals** (one place, `src/matching.py`; change a rule there and every matcher follows):
- *Same name* is **exact** (identical after case, punctuation and "&"/"and") or **similar** (the distinctive words of one name, ignoring generic ones such as Medical, Centre, Surgery, Practice, Limited, are all in the other: "Tower Hill Partnership Medical Practice" and "Tower Hill Partnership"). A match is taken only when exactly one candidate fits, and candidates are already limited to the same address.
- *NHS Jobs employer to a practice* (`jobs.candidates_for`): the practices at the employer's postcodes; link automatically on one exact or similar match; several fits or differing names go to the review list. *To a network:* one network with the same normalised name; or, for a PCN, an employer whose distinctive words equal exactly one PCN's (a services company such as "Armley PCN Services Limited") and every practice at its postcodes is in that PCN. Linked automatically means status `auto` (rejectable in Signals > Job matches); confirmed and rejected decisions are never overwritten, and signals already raised for an employer that becomes linked are filed against it.
- *ODS branch record to a practice* (`branches.resolve`): operated by a practice we hold is a real branch; otherwise matched by address and name (see Branch resolution below).
- *HubSpot company to a practice* (`hubspot_sync.py`): by ODS code; the audit flags a name difference only when the name and the postcode both differ.
- *Role titles* (`jobs.ROLES`): a title is matched against the first matching role pattern, so list the more specific ones first (records roles win over digital ones).
Not automatic by design: anything with several candidates, a different name at the address, or no practice there; those wait for a person.

**NHS Jobs scan protection**: the feed is about 125 requests per scan, so the pipeline records each successful scan in `kv_state` (`jobs_scan`) and skips the scan within 18 hours (`JOBS_MIN_INTERVAL`; set `JOBS_FORCE=1` to override), however often the pipeline is run. If NHS Jobs answers 403 to GitHub's network (it did from 21 Oct 2026), the scan is not retried against the block and reads each page through the `jobs-feed` edge function (Supabase's network; only the service role key may call it, `verify_jwt` is off because the function proves the bearer token is a service key by reading `kv_state`, which only that key can read). The run stats show `jobs_via` (`direct` or `supabase`), `jobs_skipped` or `jobs_error`, and a failed scan posts a Slack alert. A `kv_state` row `jobs_pause` (`{"until": ISO time, "why": text}`) stops the scan until that time, then clears itself.

**Branch surgeries** (migration `20261022000038`, table `practice_branches`): ODS lists branch surgeries (role `RO96`, about 2,500 active) as separate organisations whose list size sits on the parent practice, so they are not rows in `gp_practices` (that would double count patients, TAM and ARR). The daily pipeline (`branches_step`) loads them in capped batches (`BRANCH_DAILY_CAP`, 2,000 a day, never fetched first, then older than 90 days), reads the parent from the active `RE6` ("is operated by") relationship, and looks up the parent's name where it is not a practice we hold. `kind` says what the parent is: `gp_practice` (we hold it), `gp_not_held` (a GP practice that is closed or outside our England list) or `non_gp` (any other organisation, e.g. a community site). In a network profile (PCN, group, federation, ICB) each practice with branches has a collapsed "+N sites" chip that expands to the full site details (branches have no profile of their own), and the top tile shows the network's branch-site count; sites add nothing to its patients or ARR. Searching a branch's name, code or postcode finds its parent practice (with a "Branch: …" chip) and the parent's profile has a Branch sites section; branches whose parent is not a practice in Atlas show in a strip above the table. The run stats record `branches_active`, `branches_not_gp`, `branches_parent_not_held`, `branches_no_parent` and any `branches_error`.

**Branch resolution** (migration `20261022000040`, `src/branches.py`, Data > Branch sites): ODS holds two kinds of branch record. Where ODS says a GP practice we hold operates the record (relationship `RE6`), it is a real branch of it (a 9-character code is the practice's own code plus a suffix, `M85624001` belongs to `M85624`, true for all 1,976 such records; some 5-character codes are real branches too). Otherwise it is a listing made by an operator (South Doc Virtual Services is a GP co-operative running virtual services for the MyHealthcare federation, not an owner of the practices, and the Y-coded organisations are not GP practices), and `resolve` sorts it, by address and name (only for those not operated by a practice we hold), into: `duplicate_branch` (repeats a real branch at the same address), `duplicate_practice` (repeats a practice we hold), `hosted` (a differently named building at the address of exactly one practice: needs a decision), `shared` (a building with several practices) or `other` (hospital, urgent care, PCN hub: no practice there). `match_status` is `auto`, `probable` (similar name or single twin) or `review` (hosted), and a person's `confirmed` or `rejected` (Data > Branch sites; the only column the browser may update) is kept while the match is unchanged. Real branches and confirmed hosted ones are listed under their practice and in network profiles; repeats are only noted on the practice (not counted twice); everything else is findable in the search strip above the practices table. The operator is recorded but never treated as the buyer. The explanations of the six types sit behind small "i" icons on the tiles (`infoIcon()` in `js/core.js`: hover, focus or tap shows a pop-over, Escape closes it), used on the Branch sites tiles, the HubSpot audit tiles and the Revenue headings and bridge note; static headings use `<span class="info-slot" data-text="...">`, a pattern to reuse wherever help text would clutter a page. Run stats record `branches_<resolution>` counts and `branches_to_review`.

**Operational dates** (migration `20261021000035`): the profile shows when a practice opened and, once it has one, closed, from the ODS API organisation record (`gp_practices.operational_start_date`/`operational_end_date`). The daily pipeline fetches them in capped batches (`DATES_DAILY_CAP`, 2,500 a day: closed practices missing an end date first, then never fetched, then older than 180 days), so the first fill takes a few days. Clinical system now lives in the profile (Practice details) rather than the table; the System filter remains.
The daily HubSpot sync (see "HubSpot sync" below) writes these fields; daily NHS loads never overwrite them:
- `contacts.hubspot_status` (`Not imported` / `Imported`), `hubspot_imported_at`, `hubspot_contact_id`: has this contact been imported into HubSpot, and when.
- `gp_practices.hubspot_company_id`, `hubspot_company_imported_at`, `hubspot_stage` (lifecycle stage, or "Ex-customer"), `hubspot_engaged`, `hubspot_customer`, `hubspot_synced_at`.
The dashboard shows them as the practice table's **HubSpot** column (Customer / Engaged / In HubSpot / Company only / Not in HubSpot), the Networks tab's **Engaged** and **Customers**, and the Revenue tab's HubSpot position.

## Data model
`gp_practices` holds one row per practice with everything collected about it. `organisations` + `org_relationships` form a graph
(practice -> PCN / ICB / provider group / federation) where every link records its source (ods, cqc, oscar), a confidence and whether
it is confirmed. `refresh_org_graph()` rebuilds the links after each daily load; the view `org_summary` feeds the dashboard's **Networks**
tab. Other tables the tool owns: `practice_branches` (branch sites), `hubspot_links` (practice to deal), `referral_groups` (referral groups priced in the tool), and `gp_practices.hubspot_contract_terms` (the latest won deal's discounts, from the HubSpot sync). Oscar data is optional: PCN, ICB and groups come from NHS ODS and CQC; Oscar adds contacts, federation and notes.

## Operating notes
- NHS patient numbers are **monthly**, so list-size/closure signals move monthly; Oscar contact changes are picked up daily.
- A failed run posts a warning to the Slack channel and is recorded in `ingest_runs`. Rejected rows (bad ODS codes etc.) go to `ingest_rejects`.
- Free-tier Supabase pauses after ~7 days of inactivity; the daily run keeps it awake. Scheduled GitHub workflows stop after 60 days without repo activity: re-enable from the Actions tab.
- Tests: `pip install -r requirements-dev.txt && python -m pytest`.

## Known limits
- Verified from GitHub runners: ODS API and ODS export respond; digital.nhs.uk and OpenPrescribing are blocked by Cloudflare.
- The GP registration file parser and the practice->PCN lookup (ODS `Rels`, role RO272) follow the published formats but have only been tested on fixtures. Check `ingest_runs.stats` after the first run (`ods_active`, `pcn_mapped`, `pcn_error`); PCN failures degrade gracefully.

- The Supabase client script is hosted in `assets/vendor/` (version in the file name) rather than loaded from a CDN, so a compromised CDN cannot inject code. To upgrade it, `npm pack @supabase/supabase-js@<version>` and copy `dist/umd/supabase.js` there.
- The Supabase advisor flags eight `SECURITY DEFINER` functions that signed-in users can call (`am_i_allowed`, `dismiss_merge_suggestion`, `link_job_employer`, `load_devolved`, `load_patient_counts`, `set_practice_closed`, `set_practice_merge`, `sync_pricing`) and three tables with RLS but no policy (`allowed_users`, `ingest_rejects`, `kv_state`). All eight functions check the allowlist inside; the tables are service-role only. Intentional, see migration `20261017000018`.
- Turn on leaked-password protection in the Supabase dashboard (Authentication) so breached passwords are rejected.

## Closures and mergers

- **ODS closed:** a practice that drops off the ODS active GP list is marked `Closed` by the daily pipeline (with a "closed" signal).
- **Closed or merged but still Active on ODS:** ODS has no successor links and closes practices late, so such a practice usually shows no NHS list size. The database suggests likely cases and a person decides in **Signals > Closures & mergers** or on the practice profile (nothing is automatic):
  - `practice_merge_suggestions`: no list size and a practice with a list size at the same postcode (ODS "Y" codes are low confidence). Buttons: *Merged*, *Closed*, *Neither*, or mark a different practice manually.
  - `practice_closure_candidates`: no list size, CQC *Deregistered*, no absorber at its postcode.
- **Confirm merger** (`set_practice_merge`): records `merged_into`, who and when; raises `MERGER_DETECTED` if a customer or engaged practice is involved.
- **Confirm closed** (`set_practice_closed`): records `closure_confirmed_at`; raises one `PRACTICE_CLOSED` signal on the practice's **PCN** listing its nearest practices (the signal can be turned off in Data > Signal settings).
- Closed and merged practices are hidden from the main list (Status filter shows them). CQC *Deregistered* on its own only raises a signal for practices with no list size (978 practices with patients show Deregistered, which is mostly re-registrations).
- Network counts still include merged and closed practices as members (they have no patients, so revenue is unaffected).

## Push pricing to HubSpot

On a practice profile, **Push to HubSpot…** (Pricing section) sends the selected product, billing, term and speed options to the practice's HubSpot deal.
1. First time: search is pre-filled with the practice name and ODS code. Pick the company, then its deal. The link is saved in `hubspot_links` after the first successful write.
2. Preview: shows the deal's Size Discount %, Speed Discount %, Term Length Discount % and Term Length (Years) that will be written, and warns when the company list size, deal Size Tier or Value per Patient differ from the tool. Ticked fields are updated on write.
3. A selected referral group adds a Referral Discount row, a note on the deal and labelled deal links (see "Referral group in HubSpot" below).
4. After the write the tool waits (up to 20 seconds) for HubSpot to recalculate **Total Discount %** and **Actual Value per Patient (Calculated)** and compares both with the tool.

Setup: create a HubSpot private app with companies and deals read/write scopes and add its token as the Supabase edge function secret `HUBSPOT_TOKEN`. The function `hubspot-push` only accepts signed-in allowlisted users and can only write the fields listed in its source. HubSpot stores the discounts as fractions (0.05 for 5%), which its Actual Value per Patient formula requires; `HS_PCT` in `js/hubspot.js` is 1.

## HubSpot sync (fills the HubSpot section of each profile)

`.github/workflows/hubspot.yml` runs daily at 08:30 UTC (and on demand: Actions > HubSpot sync > Run workflow). It reads HubSpot (read-only) and matches companies to practices on the **GP ODS Code** field, then sets:
- **Customer**: company lifecycle stage is Customer, or any associated deal is Closed Won.
- **Engaged**: the company's own lifecycle stage is past New / Prospecting (Engaged, Marketing Qualified Lead, Sales Qualified Lead, Opportunity, Evangelist, Client Services). Contact stages are not used.
- the HubSpot company id, created date and lifecycle stage, and per contact "Imported" when a HubSpot contact with the same email is associated with the company.

Needs the GitHub secret `HUBSPOT_TOKEN` (the same private-app token as the Supabase edge function; read scopes are enough). Without it the step is skipped.

### Keeping HubSpot's PCN records in step with NHS ODS

The daily HubSpot sync reads the NHS ODS PCN list and, add-only: creates a HubSpot PCN record for any PCN that has practices in the tool but no HubSpot record (name, ODS code, address, town, county, postcode, parent ICB name and code, start date, phone; at most 25 per run), marks PCNs that ODS has closed as inactive with their end date, and associates every linked practice company with its PCN record when the association is missing. Anything it changes is posted to the Slack channel. It never deletes records or removes associations. Fields that fail validation (for example a malformed postcode) are left blank rather than written.

### HubSpot audit (Data > HubSpot audit)
Every HubSpot sync rebuilds `hubspot_audit` (migration `20261021000031`): HubSpot companies that carry a GP ODS Code but do not match the NHS list. It fills at the next sync (08:30 UTC or Run sync now). Fixes are made in HubSpot; the next sync drops them from the list.

### Line items on the deal

Pushing pricing also keeps one **Lalu Care line item** on the deal (the tool recognises it by its product, one of the four HubSpot products: All Report or SAR Only, Annual or Monthly). **Annual and Monthly name the contract term, not the billing: everyone is billed monthly.** The tool therefore writes the line item per patient per month: **Quantity** = patient list size, **Unit price** = the monthly list price, **Unit discount** = list price minus the calculator's net monthly price (so the line total is the contract's MRR), billing frequency **monthly** and terms **auto-renew**, with no billing period or payment count. The contract term (12 / 24 / 36 months, or a rolling month) is carried by the product and the deal's *Term Length*. HubSpot then annualises a monthly line item into the deal **Amount** (a line of £352.25 a month gives an Amount of £4,227, equal to the deal's ARR). The price is written explicitly, so it no longer depends on the product's own price. If the line item is for a different product it is replaced; other line items are never touched. After the write the dashboard reads the line item back and checks its net unit price, quantity and the deal Amount against the calculator. Needs the HubSpot token scopes `crm.objects.line_items.read` and `.write` (and `e-commerce` for products).

**Contracted list size** (deal property `contracted_patient_list_size`): the list size the contract was signed for, frozen on the deal so the company's own *Patient List Size* can keep following NHS. A pricing push writes it (and group deals write it per member) only while the deal is unsigned or the property is empty; a signed deal that already has a figure is never overwritten. The daily sync (`contract_patients`) uses it first as the contract's patient count, as long as it is within 0.35x to 2.5x of the practice's current list; otherwise it falls back to the line-item quantity, then the Amount.

**Won deals are locked.** Atlas never pushes to a deal in a won stage (Contract Signed, Closed Won, Renewal Secured). The HubSpot strip reads *won, locked. Change it in HubSpot*, the push dialog shows a warning with a link to the deal instead of a preview, and `hubspot-push` refuses a `write` to a won deal (HTTP 409) whatever the dashboard sends. A signed contract is changed by hand in HubSpot.

### Creating a deal from the tool

When a company has no deal (or the right one is missing), **Link deal > + Create a new deal** opens a form where every field is editable: deal name (default "lead contact - company"), pipeline and stage (default Sales Pipeline / New), deal type (New Business), product / service (ReportSure - Managed Service), owner (the signed-in user's HubSpot owner, matched by email), close date (today + 60 days), amount (the calculator's annual revenue) and which of the company's contacts (up to 5) to associate. Creating the deal ("Create deal and push pricing") writes the pricing straight away on the same page (size tier, value per patient, commercial model, discounts, term and the line item) and checks it against HubSpot, with no second confirmation. Needs the token scope `crm.objects.owners.read` to list owners.

**The company page.** HubSpot > Continue (or Add to HubSpot, then Continue) opens one page that walks the order **Company > Contacts > Leads > Deals**: a progress strip, the contacts already on the HubSpot company (with **Add n from Atlas** for Atlas contacts that are not in HubSpot yet), the company's leads with **+ Create lead**, and its deals with **+ Create deal**; choosing a deal goes to the pricing push. The highlighted card is the next step. It needs the token scopes `crm.objects.leads.read` for the lead list.

**Create a lead.** **+ Create lead** on that page makes a lead in HubSpot's Prospecting Pipeline at New (type New business, Prospecting Campaign (defaults to **Atlas**, the source tag for leads made here), owner defaults to the signed-in user, ODS code stored on the lead) associated with the chosen contact (primary) and the company. If the contact already has an open lead the form warns and needs "Create anyway". Per Unmatched's workflow documentation, a lead in that pipeline makes `UM | Lifecycle Stage Progression` set the contact to the Prospecting lifecycle stage (when it is New or Engaged); a lead created by API gets no owner rotation or sequence enrolment, and moving it to Discovery Call Scheduled (by hand) sets SQL. Not tested against live HubSpot yet. Needs the token scopes `crm.objects.leads.read` and `crm.objects.leads.write`.

### Referral group in HubSpot
`HS_REFERRAL_WRITES` is on: HubSpot's Total Discount % includes `referral_discount`. "Price alone" on that card opts out for the session. **Create the referred practices' deals** (`js/hubspot-group.js`): once the referring practice has been pushed, its Referral group strip shows "Create the missing deals". The screen lists each referred practice with what will happen (create company and deal, create deal, or why it is skipped: already a customer, already has a deal, no active record), lets you pick the deal owner and close date, then for each one creates the company if needed (no contacts; the daily sync associates it with its PCN), creates the deal in the Sales pipeline at its first stage, and pushes the group-rate pricing. Wording: the practice bringing the others is the "referring practice", the others are "referred practices" (also the HubSpot association labels).

Customer Contract section, when the HubSpot deal has no discount properties (most deals before the tool wrote them: 2 of 131 closed-won deals at 25 Oct 2026): it shows an "Effective price" row worked out from the contract value (ARR ÷ patients ÷ 12) and an "Against list" row, with a tooltip saying it cannot be itemised. ## List sizes in HubSpot
When a practice's deal already carries a line item the tool put there, the profile's plan (SAR or all reports, monthly or annual) starts from it (`hsAdoptLine` in `js/hubspot.js`), unless the user has already chosen a plan in that profile. A monthly contract is therefore not pushed as annual just because the profile defaults to annual; the preview still shows exactly what will change before anything is written.

After a pricing push the re-check also compares the deal's **Amount** with the line item's yearly value (HubSpot puts the annualised line items into Amount whoever creates them: a monthly line of £352.25 gives an Amount of £4,227, the same as the deal's ARR), and the line item's net unit price and quantity with the tool. A mismatch is logged as a failed check and shown in red, which is how a workflow that rewrites the price or the Amount would be caught.
- **Customers are left alone by default; an Include customers switch changes that.** `gp_practices.hubspot_list_size` mirrors the Patient List Size on the HubSpot company (read by the daily sync). A customer's contract size is on the Lalu Care line item and HubSpot's native ACV, MRR and TCV are worked from it, so the company's list size could follow NHS (and go to 0 when a practice merges), but as a precaution the automatic update skips every `hubspot_customer` company unless `app_flags.list_size_sync.include_customers` is true. The switch is **Include customers** beside *Update automatically* in the same card, and the card says how many customer sizes are being left as they are. Flipping it keeps `enabled` and `last_month`; a customer's size changes only in the next monthly run after it is on. The profile's Contract section still shows *List size signed for*, today's NHS figure and the change. The 25% hold-back applies to everyone. The manual actions (approving a held size, the merge dialog, a pricing push that sets the company size) are separate and still work for any company.
- **Non-customers follow the NHS figure automatically, off by default.** Data > Overview > HubSpot integration > *List sizes in HubSpot* has an **Update automatically** switch (`app_flags.list_size_sync`), a **Preview changes** list, and **Review held back**. When on, the first sync after each new monthly NHS load (it compares the latest `data_month` with `app_flags.list_size_sync.last_month`, so the daily runs in between do nothing) writes changed sizes for active, unmerged practices to HubSpot in batches of 100 (`companies/batch/update`, needs the company write scope on the sync token; a failure stops the run and says why). A move of more than 25% (`SIZE_HOLD`) is held for a person to approve, one practice at a time. A **merged or closed** practice whose NHS figure is 0 is set to **0** in HubSpot too (never held back), so HubSpot's Patient List Rollup (which sums associated companies) never counts the same patients under both the practice and its successor. A practice with no NHS data at all is not zeroed.

### Expansion review flag

## Contacts from HubSpot (staging and quality checks)
Data > Data sources > **Contacts from HubSpot** reads a HubSpot "all contacts" export (zip or CSV; it needs the opt-out and hard-bounce columns) in the browser, checks every contact and stages it in `contact_candidates` (migrations 52 and 53; `load_contact_candidates`, `review_contact_candidates`). The checks live in `src/contact_quality.py` and in `js/contact-import.js` (browser twin, kept identical: tested row by row against a real export, which is never committed).
- **Email**: *direct* when the contact's first and last name are in the address (`alex.sample@nhs.net`); *shared* for `enquiries@`, `reception@`, an ODS code in the address, or the practice's name; *likely direct* / *check* otherwise.
- **Role**: *A* decision-makers (practice, business, operations, general, service and site managers, deputy and assistant practice managers, partners, directors, IT, data and digital managers and leads), *B* secondary (finance and HR managers, PCN directors, digital leads; deputy and assistant practice or business managers count as A), *x* not decision-makers (nurses, ANPs, GPs who are not partners, reception, admin, secretaries), *?* unclear (usually a blank title).
- **Status** (nothing has to be reviewed by hand): a decision-maker (A) whose address matches their name (direct, or at least part of the name) is **approved** and promoted into `contacts` (`source = 'hubspot'`, negative `contact_urn`s from `contact_local_urn` so they never collide with Oscar's); shared mailboxes become **generic** (one `practice_generic_emails` row per practice, preferring a decision-maker's mailbox, never replaced once the practice has one); opted-out and hard-bounced (unknown user, policy, other) are **suppressed**; no matching practice, not a decision-maker or a bad address are **rejected**; the rest is **held back** (status `review` in the table): role unknown (no job title), secondary role, address that does not match the name, or unclear address. Held-back contacts need no action; they are listed on the Data tab (filterable by reason) for optional spot checks and are picked up when a later export or Oscar supplies a title. Contacts with no email are skipped. On the Sept export this gives about 7,200 approved, 2,800 held back, 5,200 generic, 1,900 suppressed and 3,100 rejected.
- **Re-uploading** is the update path, keyed by the HubSpot record id: changed details (name, title, phone, company) are applied to approved contacts automatically, a changed email goes back to review, a new opt-out or bounce suppresses the contact at once, and contacts missing from the latest export are marked but kept.
- **Oscar** (`contacts_step` in `src/ingest.py`) never deletes HubSpot-sourced contacts. An Oscar contact with the same email at the same practice adopts the HubSpot one (Oscar's details win, the HubSpot id is kept and the HubSpot-sourced row is removed). A new Oscar contact is added only when its address is direct; a shared mailbox becomes the practice's generic address only if it has none from Oscar; anything else is held back and listed in `ingest_rejects`. Oscar contacts are stamped with `email_quality` and `role_tier`.

**Primary contact (the Manager column).** `gp_practices.manager_*` (shown in the Practices table and exports) comes from Oscar's primary contact; when Oscar has nobody for a practice, the daily HubSpot sync picks the most senior contactable decision-maker among that practice's HubSpot-sourced contacts (`fill_hubspot_managers`, ranked like Oscar's, deputies and assistants last) and marks them `is_primary`. `manager_source` (`oscar` or `hubspot`, migration 54) records which, and the Oscar load never wipes a HubSpot-chosen one. Migration 54 also did the first fill, so the table filled straight after the contact load.

**HubSpot audit clean-up.** A closed or merged practice whose HubSpot company is already marked Closed or Merged is no longer listed (the daily sync checks Operating status against NHS data). Any other item can be **Dismissed** from Data > HubSpot audit (one row, or all items in the current view); dismissed ids are kept in `hubspot_audit_dismissed` (migration 55) so they stay off the list when the sync rebuilds it, and **Show dismissed** lists them with **Restore**.

**Audiences use Atlas contacts first.** Expanding a practice in an audience lists its Atlas contacts (the approved, direct-address decision-makers; Oscar's too once connected), best roles first. A contact with no HubSpot id shows "Not in HubSpot yet" and cannot be ticked. "Show all HubSpot contacts" adds the rest of the company's HubSpot contacts (nurses, reception and so on). Whenever contacts are approved, skipped-to-approved or enrolled, Atlas first re-reads the ticked contacts' practices live from HubSpot and leaves out anyone who has opted out, bounced or left HubSpot since the export (`audLiveCheck` in `js/audiences.js`); the notice says who and why.

## Revenue > Patients under management
The Revenue tab has two sub tabs: **Estimates** (the original page) and **Patients under management** (`js/revenue-pum.js`): a line chart (one line per product or service type, plus a dashed total, with a hover crosshair and tooltip, 12m/24m/all-time range and clickable line toggles) of the patients customers cover, month by month, with filters for product (All reports and SAR only on by default; Self service, PAYG and Freemium off), Service (HubSpot's deal property Product / Service: *eMR* = ReportSure Self Service, *eMR+* = ReportSure Managed Service), "take churn off" or "current customers only", and a split by product or by service type. Hovering a month shows its numbers. A customer counts at the patient size in their contract, updated at each renewal (`hubspot_size_history`: for each closed-won deal in the sales, conversion or renewals pipelines, its line item quantity, else its Amount over twelve months of the net price per patient, which gives round contract sizes; the deal's own Patient List Size is not used because HubSpot keeps syncing it from the company; `hubspot_signed_size` is the latest, falling back to the company's list size) from `hubspot_first_start` (the first Service's start date, else the first won deal's close date) until `hubspot_churned_date` (the Service's *Date Churned*), so churned patients come off. Migration 56 adds those columns plus `hubspot_company_status`, `hubspot_service_name`, `hubspot_product` (all, sar, self, payg, freemium, from the Service's name) and `hubspot_product_service`; the HubSpot sync fills them (`lifecycle_fields` in `src/hubspot_sync.py`), and the profile's HubSpot section shows Product / Service, Company status, Service started and Churned. Practices with no start date are counted in the "No start date" tile and left off the chart. Only practices HubSpot still links to are included, so churn before a company was removed from HubSpot is not shown.

## Alignment of HubSpot company properties with NHS data
The sync also reads three company properties into `gp_practices` (`hubspot_org_type`, `hubspot_operating_status`, `hubspot_website`) and compares them with what NHS data says: Org Type should be *Practice*; Operating status is *Merged* when the practice merged into another, *Closed* when it is closed or inactive, otherwise *Active*. A practice's profile shows the NHS values under *Practice details* (Org type, Operating status) and HubSpot's own values inside the *HubSpot* section, flagged *Needs updating* when they do not match.

**Automatic alignment** (Data > Overview > HubSpot integration > *Alignment with NHS data* > **Keep these in step automatically**, `app_flags.alignment_sync`, off by default): each daily sync sets Operating status from NHS data on the HubSpot companies that differ, and fills a blank Org Type (a deliberate value such as Group is never overwritten), in batches of 100 (`plan_alignment` / `push_alignment` in `src/hubspot_sync.py`, logged as *alignment_sync*). Merged practices and sites that continue as branches are never changed automatically. A run of more than 100 changes (the first backfill, or a bad feed) waits for **Approve this run**. There is no import file: the website is only read, never written, since HubSpot uses it to identify companies. Branch sites and PCN/ICB/federation companies are not in `gp_practices`, so their Org Type is not managed here.

### Merged practices and sites that continue as branches
One rule: **a HubSpot company keeps the ODS code it was created with, for good.** Its Operating status says what happened to that code, and Parent Company links say who took over. Merged practices and moved sites are therefore never changed automatically: each needs links between companies. They are changed one at a time from the profile (HubSpot section > **Update HubSpot…**) or from *Alignment with NHS data > Merged and moved sites*; the dialog lists exactly what will change first (edge action `entity_change`, logged in the HubSpot activity log):
- **Merged** (`gp_practices.merged_into`): the company stays with its code and history, Org Type *Practice*, Operating status *Merged*, and the successor practice's company as its **Parent Company**. If the merged practice's site goes on as an active ODS branch of that successor (Bawtry and Blyth, Buttercross), the company is a **Branch (Site)** instead of a Practice, still marked Merged (association type 14 from the child; 13 is Child Company; `hs_parent_company_id` is read-only, so the sync reads it back and a missing link shows as *Needs updating*).
- **Closed code whose site goes on as a branch** (`siteMove` in `js/hubspot-align.js`: an active ODS branch of another practice at the same postcode with the practice's own name): the old company stays as the closed record (Operating status *Closed*, parent = the operating practice). The site gets **its own company** with the branch code (found if HubSpot already has it, else created from the ODS branch: Branch (Site), Active, same parent), the two companies are associated with each other, and, if ticked, the old company's contacts are also associated with the branch so their emails and activity show on both.
- **Traceability:** a note on each company says what changed, when and by whom; `gp_practices.hubspot_change_note` shows the same line in the profile; `practice_branches.hubspot_company_id` holds the branch's company. A customer is flagged in the dialog: its deals stay on the old company and Customer Success decides whether the contract moves.

## Audiences
The **Audiences** tab has one automatic audience per signal type. Open one to see the practices where that signal is open (newest first); expand a practice to see its contacts, read live from HubSpot (Atlas stores none), tick the ones worth messaging and **Approve selected** or **Skip selected**. Only decisions are stored (`audience_members`: contact, practice, state, who and when); suggestions are never stored. A contact approved in one audience is shown locked, with the audience named, in every other, so each contact is in one audience at a time. Contacts with no email, an opt-out or an invalid address are shown but cannot be selected, with the reason. Practices not in HubSpot cannot list contacts. Network-level signals (no practice) are not in audiences yet.
**Custom audiences:** filter the Practices table and choose **Save as audience** (it needs at least one filter), or use **+ Audience** in a practice's profile header to hand-pick. A custom audience is a live filter (`audiences.filters.criteria`, the same object the table uses: `readFilters` / `matchPractice` in `js/practices.js`), a list of hand-picked practices (`filters.pinned`), or both. Practices that start matching appear for review; ones that stop matching drop out; approved contacts are kept. In an audience, Rename and Delete (a soft delete) are in the header, and hand-picked practices have Remove. Custom audiences share the review screen with signal audiences, with the practice's size, tier and HubSpot status in place of a signal headline.
**Role filter** (both kinds): All roles / Practice managers / GPs and clinicians / Other, by job title (`audRoleOf`). Choosing a role hides other contacts and ticks the eligible ones in every practice opened so far; **Expand first 25** opens the top practices, and **Approve n ticked** approves across all of them in one action.
**HubSpot list, sequence and performance** (edge function `hubspot-push`, actions `sequences`, `audience_push`, `audience_stats`; needs the sequence enrolment write, sequence read and CRM lists read/write scopes on the HubSpot token):
- Each audience has a **Sequence** row: **Choose a sequence** lists the sequences available to the signed-in HubSpot user (`/automation/v4/sequences?userId=`), and the choice (with that user as the sender) is saved on the audience. Emails send as that user, from their connected inbox.
- **Approve ticked** stores the decision and adds the contacts to the audience's HubSpot list: a static (manual) list named "Atlas: <audience>", created on first use. **Approve and enrol** does that and also enrols them in the audience's sequence (`POST /automation/v4/sequences/enrollments?userId=`, one call per contact), after a confirmation naming the sequence and sender. Successes become **Enrolled**; a failure is shown with HubSpot's message and the contact stays Approved. Nothing is ever enrolled without that confirmation.
- A **skipped** contact is offered again ("New signal since you skipped") when a newer signal fires for that practice, for signal audiences.
- **Performance** (Audiences > Performance, and a line on each audience): for enrolled contacts, read from HubSpot's contact fields (`hs_sequences_is_enrolled`, `hs_sales_email_last_opened`, `..._replied`, `..._clicked`, `engagements_last_meeting_booked`), counted when the date is on or after the enrolment. HubSpot's per-contact enrolment endpoints returned 404 for this token, so per-step results and exact unenrol reasons are not shown. Click **Load from HubSpot** to refresh; nothing is polled.
- **Sequence status**: a badge beside each audience's sequence (and on its card) says whether the sequence is visible to its sender in HubSpot and has steps (`sequence_status` action: `GET /automation/v4/sequences/{id}?userId=`). States: Ready (with step count), In HubSpot but has no steps, Not found in HubSpot, Could not check. Approve and enrol is blocked while a sequence is known to be missing or empty.
- **A/B tests** (`audience_tests`, migration 45): one running test per audience, managed under the **A/B tests** sub tab beside Signal audiences, Custom audiences and Performance (running tests with their two arms and verdict, a picker to plan a new test, and the past tests with winner and what was learned). Inside an audience only a one-line pointer shows while a test runs. Approve, Approve and enrol and Skip are in the audience's top bar and act on every ticked contact; there are no per-practice buttons. "Plan an A/B test" picks two sequences (both from the same sender), what differs, the split (10 to 90% to A) and a minimum per arm (default 20). While it runs, enrolment places each contact in A or B (`audience_members.arm`, `test_id`), balanced to the split, and a contact keeps its arm on retry. Results per arm read from the same HubSpot contact fields as Performance; replies and meetings are the headline, opens secondary (mail privacy inflates them). The verdict is "too early" until each arm has the minimum, then a two-proportion test on replies (about 95%). Ending a test records the winner, which becomes the audience's sequence. HubSpot cannot split or edit sequences through its API, so each arm is a sequence built in HubSpot.
- **KPIs**: Opened, Replied, Link clicks (CTA), Meetings booked, MQLs created and MQL rate (MQLs ÷ enrolled; `audiences.kpis`, `audience_tests.kpis`, `primary_kpi`, migration 46). Link clicks come from `hs_sales_email_last_clicked` (any tracked link in the sequence email, so a CTA is a link click); MQLs from `hs_v2_date_entered_marketingqualifiedlead` on or after enrolment, which does not prove the sequence caused it. An audience shows up to three on its card (KPIs button inside the audience); an A/B test ticks the KPIs it shows and picks one to decide the result. The Performance table shows all of them.
